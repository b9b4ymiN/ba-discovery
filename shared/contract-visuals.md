# BA Visual Contract (foundation / draft integration)

Visuals are derived communication artifacts, not canonical records. Phase skills own reasoning, persistence and approval; the pipeline owns navigation. The renderer must never write Project Brain, create approvals, or apply changes.

Generate a visual only when it reduces decision uncertainty. Prefer a short answer for simple questions. A visual must distinguish current approved evidence, candidate meaning, assumptions and illustrative examples. Reference relevant canonical IDs and concrete source paths; never claim that a successful render validates business meaning. Pending changes remain separate from approved truth. Historical baselines are not current truth by default.

The foundation produces a DRAFT / NOT AN APPROVAL workspace only. A future phase integration may add approved/provisional sections after verifying their provenance and scoped approval. A visual is not a checkpoint and does not replace the existing question, snapshot, change or report contracts.

Use Pele for diagrams and native HTML for future wireframes. The offline artifact must not make remote requests or execute input-supplied HTML/JS. Show the original diagram source and error on failure. Use synthetic example data when illustrating an unconfirmed design. Prefer a single derived docs/BA-Workspace.html; never overwrite unrelated files. The existing report shell and 15-section order remain unchanged.

The workspace is a snapshot: show source paths and fingerprints; check declared source freshness on resume or before reuse. An offline file cannot observe arbitrary project changes; verify explicitly. Fingerprints do not attest semantic correctness or completeness of the declared source list.
